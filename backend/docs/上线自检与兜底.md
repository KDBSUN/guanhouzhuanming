## 零、一条重要发现（B5 实测出来的真漏洞）

**限流可以被伪造的 `X-Forwarded-For` 绕过 —— 已被实测复现。**

原因是两层信任叠加：

1. **uvicorn 的 `--proxy-headers` 默认开启**，且默认只信任来自 `127.0.0.1` 的转发头；
2. 我们在应用层写了"默认不信任 XFF"（`TRUST_PROXY` 默认关），但它拿到的是**已被 uvicorn 改写过的**
   `request.client`，于是应用层判断被架空。

实测（本机直连 8000，伪造 70 个不同 XFF，打 `/api/records`，限额 60/分钟）：

| 启动方式 | 结果 | 说明 |
|---|---|---|
| 默认（proxy-headers 开） | `200×70`，**429×0** | 服务端给每个假 IP 建了独立桶 → 限流形同不存在 |
| `--no-proxy-headers` | `200×60`，**429×10** | 只有一个桶 `records_add:127.0.0.1`，第 61 次起拒绝 ✅ |
| `--no-proxy-headers` + `TRUST_PROXY=1`（模拟 nginx 覆写 XFF） | 每个真实 IP 各自 `200×60 → 429` | 两个 IP 两个桶，互不连坐 ✅ |

**结论（两条，缺一不可）**：
- **直连公网**：启动必须带 `--no-proxy-headers`；
- **确实在 Nginx 之后**：保留 `--no-proxy-headers` + 应用侧 `TRUST_PROXY=1`，
  **且 nginx 必须覆写 XFF**（`$remote_addr`，不是 `$proxy_add_x_forwarded_for`）。

`GET /api/health` 里新增 `proxy_check`：如果 uvicorn 正在替我们信任 XFF，会直接给出
`uvicorn_rewrote_client: true` 与告警文字——**这个检测本身就是验证手段**：
带上 `-H "X-Forwarded-For: 1.2.3.4"` 请求一次，看 `client_seen` 是不是变成了 `1.2.3.4`。

```bash
# 正确：直连（client_seen 应恒为真实来源，不会被 XFF 带跑）
python -m uvicorn main:app --host 127.0.0.1 --port 8000 --no-proxy-headers
curl -s "http://127.0.0.1:8000/api/health" -H "X-Forwarded-For: 1.2.3.4" | python -m json.tool | grep -A4 proxy_check
```

## 一、Nginx（B3 CORS 配套 + B4 代理头）

**后端已改**：`allow_origins=["*"]` 已收紧为「默认只放行本机开发端口 + `.env` 里 `CORS_ORIGINS` 显式声明的域名」，
且配置里出现 `*` 时会在启动日志里告警、并关闭 `allow_credentials`。
所以现在**必须**在 `backend/.env` 写明域名：

```ini
CORS_ORIGINS=https://你的域名,https://www.你的域名
TRUST_PROXY=1                 # 仅在下面这份 nginx 配置生效时打开
```

```nginx
server {
    listen 443 ssl http2;
    server_name 你的域名 www.你的域名;
    # ssl_certificate / ssl_certificate_key ...（证书路径按你的实际填）

    # 前端静态产物（frontend/dist）
    root /srv/bagua/frontend/dist;
    index index.html;
    location / { try_files $uri $uri/ /index.html; }

    # 后端
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;

        # ★ 关键：**覆写**而不是追加。用 $proxy_add_x_forwarded_for 时，
        #   访客自带的假 XFF 会留在链首，配合 TRUST_PROXY=1 就等于让访客自己选桶。
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;

        # SSE（AI 流式断语）：关缓冲，否则会攒着一次性吐
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 300s;
        chunked_transfer_encoding on;
    }
}
```

自查：`curl -H "X-Forwarded-For: 1.2.3.4" https://你的域名/api/health` —— `client_seen`
应当是你的真实出口 IP（说明 nginx 覆写生效、应用按真实 IP 分桶）。

## 二、systemd（D2 开机自启）

`/etc/systemd/system/bagua-api.service`：

```ini
[Unit]
Description=Bagua FastAPI (uvicorn)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/srv/bagua/backend
EnvironmentFile=/srv/bagua/backend/.env
# ★ 时区：**必须**。后端有 7 处用"现在几号/几时"决定结果（择日起点、应期起点、
#   岁运、黄历、起卦默认时辰）；云镜像默认常是 UTC，于是北京时间每天 08:00 之前
#   "今天"会被算成昨天——黄历/择日/应期整体错一天，且没有任何报错。

RestartSec=3
# 日志交给 journald（轮转见下）
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

## 三、日志轮转（D3）——**保留期不得少于 6 个月**

> ⚠️ **本节初版把保留期写成 2 周，那是错的，已修正。**
> 依据：《网络安全法》第二十一条（三）——采取监测、记录网络运行状态、网络安全事件的技术措施，
> 并按照规定**留存相关的网络日志不少于六个月**。
> 《人工智能生成合成内容标识办法》第九条另有"留存提供对象信息等相关日志不少于六个月"的同向要求。
> **2 周不满足任何一条。**

**推荐**：日志走 journald（上面的 unit 已如此），由 journald 统一轮转：

```ini
# /etc/systemd/journald.conf
[Journal]
# 保留期 ≥ 6 个月（26 周）。容量必须一起放大，否则容量先到、保留期失效。
MaxRetentionSec=26week
SystemMaxUse=2G
SystemMaxFileSize=100M
```

```bash
sudo systemctl restart systemd-journald
journalctl --disk-usage
journalctl --since "7 days ago" | head        # 抽查能查到
```

⚠️ **容量与保留期要一起看**：journald 是"容量与时间谁先到算谁"。线上访问日志增长较快时，
2G 未必撑得到 6 个月——**上线一个月后用 `journalctl --disk-usage` 复核一次**，
不够就调大 `SystemMaxUse`，或把访问日志单独落文件配 logrotate。

若你偏要写文件（例如 `/var/log/bagua/api.log`），logrotate 也要满足 6 个月：

```
# /etc/logrotate.d/bagua
/var/log/bagua/*.log {
    daily
    rotate 190          # ★ 190 天 > 6 个月（不是 14）
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
```

## 七、时区（B7）——**一行命令，但错了会静默算错日期**

这一项和别的不一样：它错了**不会报错**，只会让日期整体差一天，用户以为"算得不准"。

**受影响的位置**（后端 7 处，都取本地时区的"今天/现在"）：

| 文件 | 位置 | 错一天的后果 |
|---|---|---|
| `zeri.py` | 65 | 择日宜忌表整体错一天 |
| `yingqi.py` | 95、157 | 应期扫描窗口错一天 |
| `liunian.py` | 41 | 流年判定，跨年附近可能错一年 |
| `main.py` | 743、800 | 首页黄历条的"今日"错一天 |
| `main.py` | 1146、1158 | 起卦默认时辰错 |
| `engine.py` | 427 | — |
| `feedback.py` | 50 | 校验对账日期错一天 |

**为什么云服务器上一定会撞上**：`datetime.now()` / `date.today()` 取的是**服务器本地时区**，
而 Ubuntu/Debian 云镜像默认常是 **UTC**。一旦是 UTC，**北京时间每天 08:00 之前，
本站认为"今天"是昨天**。

修复（两处都做，互为保险）：

```bash
sudo timedatectl set-timezone Asia/Shanghai
timedatectl                      # 应显示 Time zone: Asia/Shanghai (CST, +0800)
date                             # 应显示 CST
```

```ini
# systemd 单元里再加一道（见"二"节的 unit）：
Environment=TZ=Asia/Shanghai
```

验证：

```bash
python tools/selfcheck.py -v      # 看 B7 一行
curl -s http://127.0.0.1:8000/api/health | python -m json.tool | grep -A6 '"timezone"'
```

`/api/health` 的 `timezone` 字段给两个**含义不同**的标记，别混：
- `ok: false` —— 配置不对（时区不是 +08:00），**隐患**；
- `date_differs: true` —— 本地日期与北京日期**此刻已经不同**，**正在出错**。
  （UTC 机器上它只在北京时间 00:00–08:00 为 true，所以不能单独当判据，`ok` 才是。）

**刻意没有做的事**：没有在代码里 `os.environ['TZ']='Asia/Shanghai'` 强行改。
那会把"服务器配错了"这件事**盖住**——本项目对这类问题的取向一直是"宁可大声失败，
不要静默修好"，所以选择了启动告警 + 健康检查暴露 + 自检脚本退出码，三处都喊。

## 八、每日配额与优雅降级（D6）

`rate_limit` 与 `quota` **管的不是同一件事**，别搞混：

| | 管什么 | 粒度 | 上限 |
|---|---|---|---|
| `rate_limit` | **多快** | 分钟级滑窗 | **没有总量上限** |
| `quota` | **多少** | 每日总量 | 有一天最多花多少钱的天花板 |

只有分钟限流时，单个 IP 一天能打 30×60×24 次——账单上没有天花板。
这正是"400 次/天"那个数当初被算出来是预算 5.8 倍的原因。

**三道闸**（顺序是"先告警、后降级"）：

| 闸 | 值 | 行为 |
|---|---|---|
| 单 IP 每日 | **50 次** | 超出即降级。故意远大于真人用量（3~5 次），因为运营商大 NAT 下多人共用一个出口 IP |
| 全站软阈值 | **80 次** | **只发一封告警邮件**给站长，不拦任何人 |
| 全站硬阈值 | **100 次** | 降级为「仅排盘不解卦」 |

**2026-09-19 由站长下调**（原为 软 100 / 硬 200），理由是"限制使用 ai 次数到 100 次"。
软阈值同时降到 80：**软硬相等的话告警与关闸同时发生，那封邮件永远来不及起作用**——
等于没有告警。这一条不是审美，是这个机制能不能用的前提。

**成本换算**（依据 `deepseek-v4-flash` 空闲时段单价，见下）：
100 次/天 ≈ **2 元/天 ≈ 60 元/月**，与 500 元/年的预算相称。

**计入口径**：梅花解卦、六爻断卦、**多轮追问**、专业模式——**都算**。
追问必须计入：它同样调 LLM 花钱，不计的话一个人能靠无限追问把当天成本放大数倍。
语音识别（ASR）**不计入**：它走百炼、按秒计费，不是"AI 解读"，
计入会让"AI 解读额度"这个说法与用户实际感受对不上。

**⚠️ 起卦与排盘不占额度**（2026-09-19 起）：梅花 `/api/meihua/divine` 与六爻
`/api/liuyao/divine` 各多了一个 `ai` 开关，`ai=false` 时**不调 LLM 也不调
`quota.acquire()`**。理由：卦象、体用、处方五行、应期全是确定性计算，不花上游一分钱；
对不花钱的东西扣额度，用户就不敢看盘了，而那个盘本来就是本站最该被看到的部分。
前端因此拆成两步——先出盘（免费），用户看过再点「AI 解卦」（扣 1 次）。

> **口径变了，读旧日志时注意**：`/api/mingju/quotes`（查典籍原文）与 `/api/mingju/check`
> （命卦校验）本来就**不计入**，它们是纯代码。真正计入的只有上面那四处 LLM 调用。

**降级时到底关掉了什么**（这是这套设计的要点）：

| 仍然可用（全是确定性计算，不花钱） | 被关掉 |
|---|---|
| 卦象、体用、动爻、互卦变卦 | AI 白话解读 |
| 处方五行、应期日期、择日 | 多轮追问 |
| 六爻排盘、用神、六亲、神煞 | 专业模式的**起卦方式识别** |

**为什么不整站关掉**：AI 只是本站的一层。额度用尽时用户仍拿到完整的"术数部分"，
少的只是一段白话。关整站 = 拿最贵的代价（用户全跑光）去省最便宜的钱（几元 API 费）。

**专业模式为什么连卦都给不出**：它**必须先由 AI 认出起卦方式**才能起卦，认不出来就没有卦可排。
这里刻意**不**退化成时间占——用户描述了一件事、却拿到一个时间卦，那是**替用户悄悄换了一个卦**，
比"今天用不了"严重得多。所以那里如实告知，并指向仍然可走的「快速起卦」。

**改数值不用改代码**（`backend/.env`，改完重启后端）：

```ini
QUOTA_IP_DAILY=50        # 单 IP 每日
QUOTA_SITE_SOFT=80       # 全站软阈值（发邮件）
QUOTA_SITE_HARD=100      # 全站硬阈值（降级）
AI_MAX_TOKENS=8192       # 解卦输出上限（六爻／梅花）
AI_CHAT_MAX_TOKENS=4096  # 多轮追问输出上限
```

**计数落在 `backend/quota.db`**（SQLite 单表）。为什么不用内存：内存计数在重启/崩溃后清零，
等于"当天额度可以靠重启白送"。这份文件**刻意不进备份清单**——备份是给用户数据用的，
防刷计数器丢了只是重新计起。

> ⚠️ **本机开发时，你和测试脚本共用一个 IP**。所有请求的来源都是 `127.0.0.1`，
> 所以**本地跑十几次真 AI 调用就能把单 IP 那 50 次吃光**，然后自己在浏览器里点不动「AI 解卦」
> （表现是降级提示，不是报错，很容易误以为是功能坏了）。2026-09-19 实测撞上一次。
> 三条对策，按推荐次序：
> ① **调试优先用 `ai=false`**（只排盘，不扣额度）或 `TestClient`——它们根本不碰上游；
> ② 需要真出文时，用 `quota.reset()`（清当天计数，返回删掉的行数）复位；
> ③ 长期做法：给开发环境设 `QUOTA_IP_DAILY=1000`（`backend/.env`），别让调试撞生产阈值。

**重置按北京时间 0 点**，与服务器时区无关（`quota.py` 显式用 +08:00 算）。
降级文案向用户承诺"明日 0 点恢复"，这句话必须真的成立，不能取决于 B7 有没有设对。

**告警邮件**：越过软阈值时发一封到 `FEEDBACK_TO`（复用已有 SMTP）。
只发一次（标志落库，重启也不重复）。邮件里写明：当天用量、预估上限花费、
以及**若确属真实增长该改哪个环境变量**。

## 九、自检工具（一条命令跑完上面几项）

```bash
cd backend
python tools/selfcheck.py                          # 测本机后端
python tools/selfcheck.py --base https://你的域名    # 测线上（**经 nginx，这才是真正要测的**）
python tools/selfcheck.py -v                       # 打印每项细节
python tools/selfcheck.py --skip-bucket            # 跳过分桶实测（它会打满靶点一分钟额度）
```

退出码 0 = 全过、1 = 有硬失败，可直接接 cron/CI（与 `check_balance.py` 同约定）。

它检查：**B7 时区**、**B3 CORS**、**B4/B5 代理头与限流分桶**、**D4 余额**、**D6 配额**。

**B5 是怎么测的**：拿一个便宜端点（`/api/meihua/waijing`，60 次/分钟、不调 LLM、不写库）
连发 70 个**互不相同**的伪造 `X-Forwarded-For`，数真实的 429。

判定表：

| `app_trust_proxy` | 结果 | 判定 |
|---|---|---|
| False | 出现 429（只有一个桶） | ✅ 直连公网的正确形态 |
| False | **一个 429 都没有** | ❌ **限流可被伪造绕过**（uvicorn 改写了 client） |
| True | 出现 429 | ✅ 请求确实经过了一个会**覆写** XFF 的代理 |
| True | 一个 429 都没有 | ⚠ 直连后端时无法判定（TRUST_PROXY 本就依赖前置代理）；**用 `--base 域名` 复测** |

为什么必须实测：限流按什么分桶取决于**两层**叠加——uvicorn 的 `--proxy-headers`
（**默认开**，且默认信任来自 127.0.0.1 的转发头）会在进应用之前改写 `request.client`；
应用层的 `TRUST_PROXY` 只是第二层。只要第一层开着，第二层写"不信任"也是白写。
**光读配置永远发现不了，所以这里发真的请求。**

## 十一、走大陆路线的前置义务（C6 展开）

站长 2026-09-17 定的是**方案①：大陆服务器 + 完整 AI**。除了 ICP 备案，还多一套**独立的**义务，
两套不互相替代：

### 生成式 AI 的"三轨制"

| | 算法备案 | **大模型登记** | 大模型备案 |
|---|---|---|---|
| 你是谁 | 算法服务提供者 | **调用已备案模型 API 的服务方** ← 本站是这类 | 自研/微调模型 |
| 周期 | 2~4 个月 | 1~3 个月 | 6~8 个月 |
| 关键 | **所有 AI 服务都要做** | 调 API、不改输出 | 自己训练了模型 |

**算法备案与大模型登记是并行必办项，不是二选一。**

### 三条必须知道的事实

1. **"DeepSeek 已经备案了，我调 API 就不用管"是错的。** 通过 API 直接调用已备案模型能力的应用，
   由**地方网信办**开展「登记」。模型厂商的备案覆盖的是"原厂直接向用户提供服务"，不覆盖调用方。
2. **本站有一处需要留意**：`deterministic_conclusion` + 外应参断是**先由代码判定、再把结论作为
   只读上下文交给模型**。若被认定为对模型输出做了"实质性修改"，可能被要求从「登记」升级为
   「备案」（1~3 个月 → 6~8 个月）。**申报前如实说明这条实现，让属地网信办判断**，不要自行归类。
3. **已有执法案例**：2026-03 无锡一案，某公司调 API 提供 AI 服务但未做登记、未做安全评估，
   被约谈并**责令下线**。同期"清朗·整治AI应用乱象"处置违规 AI 产品 14,000 余款。

### 后果阶梯

| 情况 | 后果 |
|---|---|
| 未备案 + **主动补办** | 从轻处理，通常不罚款 |
| 未备案 + 被网信办发现 | 责令暂停服务 + 依法处罚 |
| 未备案 + **被举报或引发舆情** | 上述处罚 + 可能移送其他部门联合处置 |

最后一行对本站尤其要紧：占卜类内容**被举报的概率天然高于一般 AI 应用**。

### ⚠ 决定买服务器之前必须先问清的一件事

**先分清"要不要办"，再谈"能不能办"。** 这两问的答案完全不同：

| 你的站是什么 | 要不要 AI 备案/登记 | 主体门槛 |
|---|---|---|
| **纯确定性规则引擎**（排盘、装卦、六亲、旺衰、动爻、模板断语——全部代码算） | **不需要**（不构成"生成式人工智能服务"） | **个人主体 + ICP 备案即可** |
| **调 API 做大模型生成**（白话解读、多轮追问） | **需要**：大模型登记 + 算法备案 | 材料要求**营业执照/市场主体资质** → 纯自然人办不了；注册**个体工商户**是可行路径 |

**判据不是"页面上有没有 AI 字样"，而是"输出是不是模型生成的"。** 这一条很实用：

> **同一个卦、同样的问题，连问两次**——
> 输出**逐字相同** → 规则/模板引擎，不需要 AI 备案；
> 输出**措辞不同** → 大模型生成，进 AI 监管。

#### 关于"个人主体也能做出 AI 解卦站"这类反例（**已于同日更正，见下**）

> ⚠️ **本小节初版判断错了一半，站长本人取回了点开后的真实输出，据此更正。**
> 错在**由观察直接外推**：我观察到"未登录可见的结论/建议是模板句"，就推断
> "它可能不需要 AI 备案"。**观察是对的，推断是错的**——那只是它的第一层，
> 第二层（点按钮后）是货真价实的大模型输出。教训与本站 R6 元规则同源：
> **不能用一个载体的观察去断言另一个载体**。

**站长取回的两段真实输出**（同一课盘、不同所问），判定为模型生成，取证五条：

1. **同一课盘、换一个所问，用神与推理链整段不同**：
   问"事情受阻"→"以官鬼为阻力象，但四课无官鬼；**转看**用神应取日干乙木之耗泄——妻财辰土"；
   问"测试"→"用神取父母爻（主文书、知识、标准）兼看朱雀"。
   **"转看"是推理中的自我修正语，模板只填槽、不会"转看"。**
2. **应期结论随取用而变且各带干支推理**：前者甲辰日/丙辰日，后者"寅冲申贵人动，引动昼贵申解空"。
3. **自由造句的现代语体**："所有判断皆缺乏现实锚点"、"此时信息承载力增强"、"实为执行层卡顿"——
   传统术语与现代咨询语体混用，是模型输出的典型指纹。
4. **页面自述"通常需要几十秒"**：规则引擎是毫秒级返回。**这是最硬的一条。**
5. **五节长文结构**（总断/用神与四课/三传吉凶/应期/行动建议），段落连贯论述而非短模板句。

**把握程度**：约九成。剩下的一成留给"极其庞大的预制句库 + 极复杂的规则编排"这种理论上可能。

**更正后的结论（三条，互相独立）**：

1. ✅ **"个人主体的境内站在跑 AI 解卦"是事实**——这个样本成立，
   所以"**主体上做不到**"这个担忧可以放下（我之前那条"纯自然人办不了"至少不是实践中的硬障碍）。
2. ❌ **但它仍不证明"这样合规"**：该站页脚**只有 ICP + 公安，没有上线编号**（河南网信办公告明写要公示），
   且**没有任何"AI 生成"标识**（《人工智能生成合成内容标识办法》第四条要求显式标识），
   文案也刻意用"智能/专业算法"而非"AI"。→ 更像**"没做 AI 登记在跑"**，而非"个人办成了登记"。
3. 🔁 **"别人在跑"≠"你不会被查"**。这类监管是抽查 + 举报驱动；处罚针对的是**你的站**。
   找到一个跑着的先例，只证明"它还没被查"。

**另一个有价值的发现**：该站是**两层架构**——免费即时可见的规则模板层（结论/建议短句）
+ 点按钮后几十秒的模型层（五节长文）。**这与本站的"确定性层 + AI 语言化层"结构完全同构**，
是本项目结构上最接近的公开样本，值得作为形态参照。

> 证据强度：第 1、2 条（观察与更正）来自**站长实测取回的真实输出**（强）；
> "官方要求公示上线编号"来自**网信办官网原文**（强）；
> 而"注册个体工商户即可办 AI 备案"仍来自社区博客（**弱**），是**待确认**项。

### 找哪个网信办：属地 = **主体注册地**，不是服务器所在地

| 办什么 | 去哪 |
|---|---|
| 大模型**备案**（自研/实质训练） | **企业工商注册地所在省级网信办**（省级初审 + 国家网信办终审） |
| 大模型**登记**（只调 API） ← **本站属这类** | **属地省级网信办**（省级审核） |
| **算法备案** | [beian.cac.gov.cn](https://beian.cac.gov.cn)（省级初审 + 国家复审） |

- **用户遍布全国也只备案一次**，通过后服务可合法面向全国；跨省经营**不需要**多地备案。
- 只有在不同省份设立**独立法人子公司**并以子公司名义对外服务时，才各自单独备案
  （那叫"多主体"，不是"跨省"）。
- **服务器在哪不决定找谁，但服务器必须在境内**：材料里要求准备**部署证明**，
  "服务器部署不在境内"是常见退件原因之一。
- 个人主体的属地 = **身份证所在地（或经常居住地）对应的省级网信办**。
  是省级还是市级各地不同，直接打**省级网信办**电话问。

### ICP 备案与 AI 备案能不能并行：**不能完全并行**

AI 备案的材料清单里明确要求**主体资质含「ICP 备案号或许可证」**——所以 ICP 是前置。
但**准备工作可以并行**：

```
ICP 提交期间：同步梳理产品涉及哪些算法功能、起草算法机制说明与风险评估报告
ICP 通过之后：立即提交 算法备案 + 大模型登记
```

另有节奏差异，别混：
- **大模型登记**：属**提供服务的程序义务**，宜在公开上线前完成；
- **算法备案**：要求在「**提供算法服务之日起 10 个工作日内**」完成申报，有缓冲但不等于可拖。

注明模型名称及备案号**。→ 本站需要在 AI 标注旁（或页脚）写明所用模型的名称与备案号。

> **只要走 AI 备案这条路，服务器就必须在大陆**——这一条把"香港 + 完整 AI"也堵上了
> （香港可以跑站，但备不了 AI 案）。

### 第四种形态：**全栈出境**（不备案，彻底不进入中国合规体系）

调研时找到一个成熟的样本：`ichingquest.com`（玄机堂）。它是**完整 AI 解卦**站
（服务条款原文："结合 AI 生成解读内容"），但**没有任何中国备案**——页脚无 ICP、无公安、无上线编号。

它的技术栈与商业形态说明它是**完全在境外运营的**（隐私政策自述）：

| 线索 | 指向 |
|---|---|
| Supabase（账号与数据）、PostHog（分析）、Cloudflare（边缘） | 全栈海外 SaaS |
| **Stripe**（支付） | **Stripe 不对中国大陆主体开放**（支持港/新/日等） |
| 定价 **$39.99** 购 200 次 | 美元计价，不走人民币渠道 |
| 法律语体："款项原路退回"、"以登录所用之邮箱**寄信**" | 繁体中文法律写法，非大陆语体 |
| "支持简中、繁中、英文三种语言，满足**全球用户**需求" | 定位全球市场 |

**所以它证明的不是"个人也能备案跑 AI"，而是"不备案、全栈出海也能跑"。**
这与"香港服务器"是同一性质，但做得更彻底：连支付与后端都搬出去了。

**代价（这才是决策要点）**：没有中国法律身份 → 收不了支付宝/微信；一旦要面向境内用户收费就卡住。
**收益**：完全不用碰 ICP / 公安 / AI 登记 / 算法备案。

**它有几处做法值得抄**（与本项目"典籍作依据"的取向一致）：

1. **把「不受理的问题」写进服务条款**并**产品化**：针对他人隐私/生死/疾病的具体判断、
   涉及犯罪赌博诈骗的事项、以测试为目的反复起卦；且"经系统判定不受理的问题，**不会生成解读，
   也不扣除次数**"——合规与产品体验合成一件事。
2. **明确边界**："不判断具名投资标的的涨跌，也不构成投资建议"；"医疗、法律、生命安全等事项请咨询
   相应专业人士"。
3. **⟵ 最值得抄的一条**："同一件事不建议因为不满意答案而连续重问"，并引《蒙》卦
   「**初筮告，再三渎，渎则不告**」作依据——**用典籍给产品限制找到出处**，正是本项目的做法。
   本站六爻页目前没有这条，值得补（文案由站长定）。
4. 商业模式：免费额度 + 按次充值 + **无订阅**，与本站的"每日配额 + 硬降级"同构。

## 十二、定期审计（三件工具，2026-09-23 新增）

规则、引文、判定表都是手写条件拼出来的：**单测只验"给定输入得到期望输出"**，
验不出"这条规则在真实输入分布下根本没被走到"，也验不出"同一屏上两个结论互相打架"。
开源项目 bazi-engine 用三个脚本查这类问题（`audit_hit_distribution.js` /
`check_conflicts.js` / `check_dup_hits.js`），本站按自己的结构实现了等价的三件，
思路照搬、判据自定义：

| 命令 | 查什么 | 退出码 | 报告 |
|---|---|---|---|
| `python tools/audit_rule_hits.py` | ①判定表状态分档**全枚举**可达性（495 计数 × 5 月令 × 15 格局）②真实随机盘的**逐档命中率**（含 Wilson 95% 区间）③六爻爻旺衰／处方分支／格局命中率 ④梅花处方分支全枚举 ⑤引文键使用率（死键／未录键） | 有 ✗（恒真／结构性死档）→ 1 | `data/audit_rule_hits_report.txt` |
| `python tools/audit_conflicts.py` | 同一盘的**反常对**：喜用∩忌神（H1）、处方∈忌神（H2）、改方仍喂忌神（H3）、block 而改方＝原方（H4）、调候∩忌神未标注（H5）、同屏既开又禁（A1）、同行判词重复（A2）、grade 越出声明枚举（A3） | 有 ✗ → 1 | `data/audit_conflicts_report.txt` |
| `python tools/audit_quote_index.py --corpus` | 引文表**查重**：逐字重复（D1）、同文异书（D2）、整段包含（D3）、分段重复（D4）、同书同章异文（D5）、键前缀重叠（D6）、键与书不符（D7）、引文过短（D8），并把 53 条引文逐段与 `books/` 语料做逐字回源 | 有 ✗ → 1 | `data/audit_quote_index_report.txt` |

**读法（重要）**：`✗` 是"引擎自相矛盾／规则恒真"这类**必须处置**的硬问题；

0/N 命中的 95% 上界≈3/N，**不能把"样本太少"读成"规则已死"**；`·` 只是信息。
